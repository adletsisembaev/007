# Kitchen Cabinet Designer for SketchUp: архитектура и расчёт геометрии

Этап 1 из 7. Документ описывает архитектуру расширения, систему координат,
модель данных и формулы, по которым строится каждая деталь. Код на этапе 1
ещё не пишется. Все следующие этапы опираются на этот документ.

---

## 1. Цели и ограничения

| Требование | Решение |
|---|---|
| SketchUp 2024+ (Ruby 3.2) | Используем только давно существующие методы API (список в §10) |
| Интерфейс | `UI::HtmlDialog`: HTML, CSS и JS лежат отдельно от Ruby |
| Единицы | В интерфейсе и параметрах всё в мм (Float). В дюймы (`Length`) переводим только в момент создания `Geom::Point3d` через `Numeric#mm` |
| Undo/Redo | Одна операция `start_operation … commit_operation` на одно действие пользователя, при ошибке `abort_operation` |
| Без внешних зависимостей | Только stdlib Ruby (`json`) и SketchUp API |
| Без интернета | Все ресурсы локальные, CDN не используется |

Предлагаемая структура немного отличается от исходной. Причины изменений
перечислены после дерева.

```

kitchen_cabinet_designer/

  locales/

  geometry/

  make_icons.py                        # SVG/рисунок → PNG 24/32 (Pillow)
```

**Почему структура изменена:**

1. **Имена в нижнем регистре и уникальный префикс.** Файлы называются
   `kitchen_cabinet_designer.rb` и `kitchen_cabinet_designer/`, Ruby-пространство
   имён `KitchenCabinetDesigner`. Нижний регистр защищает от проблем с
   регистром имён на macOS и соответствует принятым соглашениям для
   расширений. Уникальное имя модуля исключает конфликты с другими плагинами.
2. **Геометрия отделена от SketchUp API.** Модули в `geometry/` содержат чистый
   Ruby: они получают параметры в мм и возвращают список деталей `PartSpec`
   с координатами в мм. В `sketchup/` происходит только «отрисовка» этих
   деталей. Благодаря этому:
   - вся математика тестируется обычным Ruby без SketchUp. Тесты проверяют
     размеры, отсутствие пересечений деталей и вписывание в габарит;
   - превью в диалоге строится из тех же `PartSpec`, поэтому формулы не
     дублируются в JS;
   - будущий экспорт раскроя (cut list) легко сделать из того же списка деталей.
3. **Папка `sketchup/` — только способ разложить файлы.** Модули из неё
   (`PanelBuilder`, `CabinetBuilder`, `Placement`) лежат прямо в
   `KitchenCabinetDesigner`. Модуль `KitchenCabinetDesigner::Sketchup` намеренно
   не создаётся: внутри пространства имён он перекрыл бы `::Sketchup`.
4. **Тексты интерфейса в `locales/*.json`.** Один файл используется и Ruby, и JS,
   поэтому для русского перевода достаточно добавить `ru.json`.

## 3. Система координат

Внутренняя единица SketchUp — дюйм. Все параметры хранятся в мм как Float,
и **только** `PanelBuilder` переводит их в `Length` (`x.mm`).

**Локальные координаты определения шкафа (ComponentDefinition):**

```
          Z (вверх, синяя)
          |
          |     Y (вглубь, к стене, зелёная)
          |    /
          |   /
          |  /
          | /
          O──────────── X (ширина, слева направо, красная)

O = передний-левый-нижний угол габарита шкафа
```

- **X** от 0 (наружная плоскость левой боковины) до `W` (наружная плоскость правой).
- **Y** от 0 (передняя кромка корпуса) до `D` (задняя плоскость корпуса).
  Плоскость стены находится на `Y = D + wall_gap`.
- **Z = 0:**
  - для **нижнего шкафа** это уровень пола, то есть низ ножек или цоколя.
    Корпус начинается на `Zc = plinth_height`;
  - для **верхнего шкафа** это низ корпуса (`Zc = 0`). Высота подвеса задаётся
    положением экземпляра.
- **Накладные фасады** выступают **вперёд** от корпуса, в область `Y ∈ [−Tf, 0]`.
  Это осознанное решение: «начало координат = передний край корпуса», а не
  передняя плоскость фасада. Так глубина корпуса `D` не зависит от толщины
  фасада.

**Положение экземпляра (ComponentInstance) в модели:**

- **Стена по умолчанию.** Это мировая ось X (плоскость `Y = 0`). Шкафы ставятся
  перед ней. Начало координат экземпляра получает `y = −(D + wall_gap)`,
  поэтому задник шкафа оказывается на `Y = −wall_gap`. Нижний и верхний шкафы,
  созданные «в начало координат», автоматически выравниваются по одной стене.
- **Высота:** `z = elevation` для нижнего шкафа (по умолчанию 0) и
  `z = mount_height` для верхнего (по умолчанию 1400 мм от пола до низа корпуса).
- **Справа от выбранного.** Если выделен шкаф этого плагина той же категории,
  новый шкаф ставится вплотную справа. Транзформация считается так:
  `sel.transformation * translation(W_sel, (D_sel + gap_sel) − (D + gap), 0)`.
  Это работает и для повёрнутых шкафов.
- **При перестроении** (изменении параметров) экземпляр сдвигается так, чтобы
  **задняя плоскость (стена) и левая сторона остались на месте**. Поэтому при
  изменении глубины шкаф не «отрывается» от стены.

## 4. Иерархия объектов и именование

```
CABINET_600_BASE              ComponentInstance (+ определение с тем же именем)
├── CARCASS                   Group
│   ├── SIDE_LEFT             Group
│   ├── SIDE_RIGHT
│   ├── BOTTOM
│   ├── TOP | RAIL_FRONT + RAIL_REAR   (зависит от конструкции крыши)
│   ├── BACK                  (если задняя стенка включена)
│   └── SHELF_1 … SHELF_n     (если заданы полки)
├── SUPPORTS                  Group (только для нижних)
│   ├── LEG_1 … LEG_n
│   └── PLINTH_FRONT [, PLINTH_REAR]
├── FRONTS                    Group (двери)
│   └── DOOR | DOOR_LEFT + DOOR_RIGHT
├── DRAWER_1 … DRAWER_n       Group на каждый ящик
│   ├── DRAWER_FRONT_1
│   └── DRAWER_BOX_1          Group
│       ├── BOX_SIDE_LEFT, BOX_SIDE_RIGHT, BOX_FRONT, BOX_BACK, BOX_BOTTOM
└── HANGING_RAIL              Group (только для верхних, по опции)
```

- **Каждая деталь — отдельная группа.** Поэтому касающиеся грани разных
  деталей не сливаются, а дублирующей геометрии нет.
- **Фасады и ящики не входят в группу `CARCASS`.** Их можно скрыть, выделить
  или перекрасить независимо от корпуса.
- **Имя определения:** `CABINET_<W>_<BASE|WALL>`. Если такое имя занято,
  добавляется суффикс `_2`, `_3`… Проверку делает собственный хелпер через
  `definitions[name]`. В `definition.description` записывается тип шкафа, например
  «Base · 2 doors · 600×720×560».
- **Атрибут `part_role`.** У каждой группы детали есть атрибут `part_role`
  (например, `SIDE_LEFT`) и размеры заготовки в мм. Это задел под раскрой.

## 5. Модель данных и параметрический цикл

**Параметры** — плоский Hash с ключами-строками и значениями в мм или
перечислениях. Пример (сокращённо):

```json
{
  "category": "base", "cabinet_type": "two_doors",
  "width": 600, "height": 720, "depth": 560, "thickness": 16,
  "top_construction": "rails", "rail_width": 100,
  "back_mode": "inset", "back_thickness": 4, "back_inset": 16,
  "back_groove": true, "groove_depth": 8, "groove_play": 1, "groove_extra_width": 0.5,
  "support_type": "legs_with_plinth", "plinth_height": 100, "plinth_setback": 50,
  "front_mount": "overlay", "front_thickness": 18, "front_gap": 2,
  "edge_gap_left": 1, "edge_gap_right": 1, "edge_gap_top": 1, "edge_gap_bottom": 1,
  "drawer_count": 3, "drawer_heights": "0;0;0",
  "carcass_material": "KCD Carcass", "front_material": "KCD Front", "back_material": "KCD Back"
}
```

**Хранение.** Параметры хранятся в словаре атрибутов `KitchenCabinetDesigner`
на экземпляре и на определении:

- `schema_version = 1` — для будущих миграций;
- `plugin_version`;
- `params` — JSON-строка.

Атрибуты сохраняются в `.skp`, поэтому шкаф можно редактировать и после
повторного открытия модели.

**Цикл «создать»:**

```
JS: sketchup.create_cabinet(json)
 └─ Ruby: JSON.parse → Settings.merge_defaults → Validation.validate
      ├─ ошибки → dialog.execute_script("KCD.showErrors([...])"), геометрия НЕ трогается
      └─ ок → Layout.build(params) → [PartSpec…]   (чистый Ruby, может бросить исключение)
            model.start_operation("Create Cabinet", true)
              definitions.add(unique_name)
              PanelBuilder.render(definition.entities, specs, materials)
              entities.add_instance(definition, placement_transformation)
              set_attribute(...)
            model.commit_operation
          rescue → model.abort_operation, сообщение об ошибке в диалог
```

**Цикл «изменить выбранный»** (кнопка в диалоге и пункт контекстного меню
«Edit Cabinet»):

1. Параметры читаются из атрибутов выделенного экземпляра и загружаются в форму.
2. «Update» → валидация → `start_operation("Update Cabinet")`.
3. Если у определения больше одного экземпляра, пользователь выбирает:
   обновить все копии или только этот шкаф (`instance.make_unique`).
4. `definition.entities.clear!`, затем отрисовка новых `PartSpec` в то же
   определение. Экземпляр сохраняет свою трансформацию с поправкой из §3.
5. Атрибуты и имя определения обновляются, затем `commit_operation`.
   Undo откатывает всё одним шагом.

Расчёт и валидация выполняются **до** `start_operation`. Поэтому большинство
ошибок не доходит до модели вообще. Оставшиеся исключения ловятся с
`abort_operation`, и незавершённая геометрия не остаётся.

## 6. Построение геометрии одной детали (PanelBuilder)

**Прямоугольная панель (Box).**

1. Создаётся группа.
2. В её `entities` строится прямоугольная грань в плоскости XY на высоте z0.
3. Проверяется `face.normal.z`: если он < 0, вызывается `face.reverse!`.
   Это защита от известного поведения SketchUp: грани на z = 0 часто
   создаются нормалью вниз.
4. Выполняется `face.pushpull(height)`. Выдавливание идёт по нормали, поэтому
   все шесть граней получаются наружу, без вывернутых граней.

**Панель с пазом или четвертью (Profile).**

1. Рисуется замкнутый 2D-контур в плоскости, перпендикулярной направлению паза.
2. Нормаль приводится к нужной оси.
3. Контур выдавливается на длину детали:
   - паз боковины идёт вдоль Z, поэтому контур рисуется в XY и выдавливается по Z;
   - паз дна и крыши идёт вдоль X, поэтому контур рисуется в YZ и выдавливается по X.

Если `back_inset = 0`, паз выходит на кромку и становится **четвертью**
(L-контур из 6 точек вместо 8). Совпадающие точки контура удаляются до
вызова `add_face`.

**Цилиндр (ножка).** `add_circle(center, Z_AXIS, r, 24)` → `add_face(edges)`
→ нормаль вверх → `pushpull(h)`.

**Материал** назначается группе (`group.material =`), а не граням. Пользователь
может перекрасить деталь целиком, текстуры ложатся одинаково.

**Точность.** Внутренняя точность SketchUp около 0,001″ (≈ 0,025 мм).
Валидация запрещает размеры деталей меньше 0,5 мм, чтобы не возникали
«схлопнутые» рёбра.

## 7. Формулы геометрии

### 7.1 Обозначения

| Символ | Параметр | По умолчанию (низ / верх) |
|---|---|---|
| W, H, D | ширина, высота корпуса, глубина корпуса | 600, 720, 560 / 600, 720, 320 |
| T | толщина плиты корпуса | 16 |
| Tb | толщина задней стенки | 4 |
| Bi | отступ задней стенки от задней кромки (`back_inset`) | 16 |
| G | глубина паза | 8 |
| Gp | зазор в пазу (насколько стенка не доходит до дна паза) | 1 |
| Gw | дополнительная ширина паза (паз = Tb + Gw) | 0,5 |
| Hp | высота цоколя/ножек (`plinth_height`) | 100 |
| Sp | отступ цоколя от передней кромки (`plinth_setback`) | 50 |
| Tp | толщина цокольной планки | 16 |
| Rw | ширина царги | 100 |
| Tf | толщина фасада | 18 |
| g | зазор между фасадами | 2 |
| gL, gR, gT, gB | зазоры от фасада до края корпуса (накладной монтаж) | 1 (по 1 мм с каждой стороны дают 2 мм между фасадами соседних шкафов) |
| gi | зазор вкладного фасада до панелей корпуса | 2 |
| Eb, Et | удлинение фасада вниз/вверх (`front_extend_*`) | 0 |
| Zc | низ корпуса | Hp (низ, если есть опоры), 0 (верх) |

**Производные величины:**

- `Dp` — глубина боковин, дна и крыши: `D − Tb` при накладной задней стенке,
  иначе `D`.
- `Yb` — передняя плоскость задней стенки:

| Режим задней стенки | Yb |
|---|---|
| inset (вставная) | `D − Bi − Tb` |
| overlay (накладная) | `D − Tb` |
| none (нет) | `D` |

### 7.2 Корпус

Схема соединения v1: **боковины на всю высоту, дно и крыша между боковинами**.
Это стандартная европейская схема. Ниже все интервалы указаны как `[min, max]`
в локальных мм.

| Деталь | X | Y | Z | Паз (при back_groove) |
|---|---|---|---|---|
| SIDE_LEFT | [0, T] | [0, Dp] | [Zc, Zc+H] | вырез X∈[T−G, T], Y∈[Yb−Gw, D−Bi], на всю высоту |
| SIDE_RIGHT | [W−T, W] | [0, Dp] | [Zc, Zc+H] | вырез X∈[W−T, W−T+G] |
| BOTTOM | [T, W−T] | [0, Dp] | [Zc, Zc+T] | вырез Z∈[Zc+T−G, Zc+T], на всю длину |
| TOP (top_panel) | [T, W−T] | [0, Dp] | [Zc+H−T, Zc+H] | вырез Z∈[Zc+H−T, Zc+H−T+G] |
| RAIL_FRONT (rails) | [T, W−T] | [0, Rw] | [Zc+H−T, Zc+H] | — |
| RAIL_REAR (rails) | [T, W−T] | [Yb−Rw, Yb] | [Zc+H−T, Zc+H] | — |

**Задняя стенка (BACK):**

| Режим | X | Y | Z |
|---|---|---|---|
| overlay | [0, W] | [D−Tb, D] | [Zc, Zc+H] |
| inset без паза | [T, W−T] | [Yb, D−Bi] | [Zc+T, Ztop], где Ztop = Zc+H−T при крыше-панели, иначе Zc+H |
| inset с пазом | [T−e, W−T+e], e = G−Gp | [Yb, D−Bi] | [Zc+T−e, Ztop+e при крыше-панели / Zc+H] |

**Почему детали не пересекаются.** Углы задней стенки заходят в паз боковины,
а он идёт на всю высоту. Дно и крыша в зоне X∈[0,T] отсутствуют. Значит,
угловая зона задней стенки находится внутри пустого паза. Тесты проверят это
автоматически (§9).

**Полки** (`shelf_count = n`) — дополнительная опция, в ТЗ её не было, но
для открытого шкафа она нужна.

- Внутренний проём по высоте: Zi0 = Zc+T, Zi1 = Zc+H−T.
- Шаг: `s = (Zi1 − Zi0 − n·T) / (n+1)`.
- Полка k (k = 1…n): Z∈[Zi0 + k·s + (k−1)·T, … + T].
- X∈[T, W−T], Y∈[Sf, Yb − Sr], где Sf — отступ от передней кромки
  (по умолчанию 0 для накладных фасадов, Tf+2 для вкладных), Sr = 0.

### 7.3 Нижний шкаф: опоры (`support_type`)

| Значение | Что строится |
|---|---|
| `legs` | Ножки-цилиндры Ø d (40), Z∈[0, Zc]. Центры: X = `leg_offset_side` (50) от наружной плоскости боковины; Y = `leg_offset_front` (100) от переда и `Dp − leg_offset_rear` (60). При W ≥ `middle_legs_from` (800) добавляется средняя пара ножек по X = W/2 |
| `legs_with_plinth` | Ножки и планка PLINTH_FRONT: X∈[0,W], Y∈[Sp, Sp+Tp], Z∈[0, Zc] |
| `plinth_box` | PLINTH_FRONT и PLINTH_REAR (Y∈[Dp−Tp, Dp]) без ножек |
| `none` | Опор нет, Zc = 0 (шкаф на подиуме или на `elevation`) |

**Проверки опор:**

- передний край передних ножек `leg_offset_front − d/2` должен быть ≥ `Sp + Tp`,
  иначе ножка «проходит» сквозь цоколь;
- ножки не выходят за габарит и не задевают друг друга по ширине и глубине;
- `Sp + Tp ≤ Dp` (для `plinth_box` — `≤ Dp − Tp`);
- высота цоколя ≥ 10 мм для любых опор, кроме `none`.

**Значения по умолчанию (этап 3):** задняя стенка накладная 4 мм; крыша нижнего
шкафа — две царги по 100 мм; опоры — ножки с цокольной планкой; одна полка.

Цоколь касается нижних торцов боковин. Это касание, а не пересечение.

### 7.4 Верхний шкаф

- Корпус по формулам §7.2 при Zc = 0. Крыша всегда панель (`top_panel`).
- `mount_height` — Z экземпляра, высота низа корпуса от пола (1400).
- `wall_gap` — расстояние от задника до стены (0).
- **HANGING_RAIL** (опция) — брус или шина сечением `Rh × Rt` (50 × 10 мм).
  - Ставится сразу за задней стенкой: Y∈[Yr, Yr+Rt], где Yr = D−Bi (inset)
    или D (overlay).
  - По Z: [H−T−Rh, H−T], то есть под крышей.
  - По X: [T, W−T], если шина помещается внутри глубины боковин; [0, W],
    если она целиком в зазоре за шкафом.
  - Проверка: `Yr + Rt ≤ D + wall_gap`. Иначе ошибка «Hanging rail does not fit:
    increase back inset or wall gap».

### 7.5 Двери и фасады

**Зона фасадов:**

| Монтаж | X | Z | Y |
|---|---|---|---|
| overlay | [gL, W−gR] | [Zc+gB−Eb, Zc+H−gT+Et] | [−Tf, 0] |
| inset | [T+gi, W−T−gi] | [Zc+T+gi, Zc+H−T−gi] | [Si, Si+Tf], Si = утопление (0) |

**Раскладка дверей:**

- **одна дверь (DOOR)** занимает всю зону;
- **две двери:** `wd = (Xmax − Xmin − g) / 2`.
  - DOOR_LEFT: X∈[Xmin, Xmin+wd];
  - DOOR_RIGHT: X∈[Xmin+wd+g, Xmax].

**Проверки:**

- ширина каждой двери ≥ 100 мм;
- при одной двери шириной > 600 мм выдаётся **предупреждение** (не ошибка);
- для inset проверяется `Si+Tf ≤ Sf` полок, иначе дверь упрётся в полки.

### 7.6 Ящики

**Высоты фасадов (сверху вниз).** Поле задаётся списком `h1;h2;…;hN`, где
значение 0 означает «авто». Доступная высота зоны `Hz` (как для фасадов).
Остаток `Hz − Σ(заданных) − (N−1)·g` делится поровну между значениями «авто».

- Если «авто» нет, сумма обязана совпасть с `Hz` с точностью до 0,1 мм.
  Иначе ошибка с подсказкой, какой должна быть сумма.
- Фасад i: Z_top(1) = Zmax, Z_bot(i) = Z_top(i) − h_i, Z_top(i+1) = Z_bot(i) − g.

**Короб i:**

| Величина | Формула | По умолчанию |
|---|---|---|
| Ширина снаружи | `Wb = W − 2T − 2·Cs` | Cs = 13 мм на сторону, под шариковые направляющие |
| X | [T+Cs, W−T−Cs] | |
| Начало по Y | `Yf = Cf` (overlay) или `Si+Tf+Cf` (inset) | Cf = 2 |
| Глубина | авто: наибольшая стандартная длина направляющей (кратная 50 мм), ≤ `min(D−30, Yb−Yf)`; или ручное значение | ручное проверяется на `Db ≤ D−30` и `Yf+Db ≤ Yb` (спец. требование ТЗ) |
| Низ | `zb_i = max(Z_bot(i), Zc+T) + Cb` | Cb = 15 |
| Высота | авто: `hb_i = Z_top(i) − Ct − zb_i`; или ручное `Hb` | Ct = 30; ручное проверяется на `zb_i + Hb ≤ min(Z_top(i) − Ct, Zc+H−T)` |

**Почему соседние коробы не пересекаются.** Ящик i+1 находится под ящиком i.

- Верх короба i+1: ≤ Z_top(i+1) − Ct = Z_bot(i) − g − Ct.
- Низ короба i: ≥ Z_bot(i) + Cb.

Значит, между ними всегда есть зазор не меньше g + Ct + Cb > 0, и
пересечение исключено при любых положительных зазорах.

**Детали короба** (dt — дно, ts — боковины):

| Деталь | X | Y | Z |
|---|---|---|---|
| BOX_BOTTOM | [x0, x1] | [Yf, Yf+Db] | [zb, zb+dt] |
| BOX_SIDE_LEFT | [x0, x0+ts] | [Yf, Yf+Db] | [zb+dt, zb+hb] |
| BOX_SIDE_RIGHT | [x1−ts, x1] | [Yf, Yf+Db] | [zb+dt, zb+hb] |
| BOX_FRONT | [x0+ts, x1−ts] | [Yf, Yf+ts] | [zb+dt, zb+hb] |
| BOX_BACK | [x0+ts, x1−ts] | [Yf+Db−ts, Yf+Db] | [zb+dt, zb+hb] |

**Проверки:** `hb_i ≥ 60`, `Wb − 2ts ≥ 50`, `Db ≥ 200`.

**Ящики допускаются только у нижних шкафов.** Для верхнего шкафа выдаётся
ошибка «Drawers are available for base cabinets only».

## 8. Валидация (Validation)

Валидация — единственный источник правил, она написана на Ruby. Работает
в два слоя:

1. **JS:** мгновенная проверка «число > 0» при вводе. Затем запрос в Ruby
   `validate` с задержкой 300 мс, и ошибки подсвечиваются у полей.
2. **Ruby:** полная проверка перед созданием. Возвращает
   `[{field:, message:}]` и разделяет ошибки и предупреждения.

**Группы правил:**

- **типы и перечисления:** числовое поле не число, значение не из списка;
- **диапазоны:** все размеры > 0; T ∈ [3, 50]; W ∈ [100, 2400];
  H ∈ [100, 2800]; D ∈ [100, 1000];
- **конструктивные правила:**
  - `2T < W`, `2T < H`;
  - паз только при `back_mode = inset`, `G < T`, `Gp < G`;
  - `Bi + Tb + Gw < D − 50`;
  - `Rw·2 < Dp` при царгах;
  - все проверки из §7.3–7.6;
- **материалы:** пустое имя заменяется именем по умолчанию.

## 9. Стратегия тестирования

Тесты пишутся честно и делятся на два вида.

| Что | Как проверяется |
|---|---|
| Формулы, валидация, раскладка фасадов и ящиков | **Реально запускаются** Minitest-тесты на Ruby 3.3 в этой среде, без SketchUp: проверка размеров, симметрии, суммы высот |
| Отсутствие пересечений деталей | Тест разбивает каждую деталь на AABB-боксы (профиль с пазом = объединение 2–3 боксов) и проверяет, что объём попарного пересечения равен 0 для 40+ комбинаций параметров |
| Регистрация, тулбар, HtmlDialog, обмен JS ↔ Ruby, создание групп, Undo/Redo, сохранение и открытие .skp | **Только проверка кода**: SketchUp в этой среде запустить нельзя. В `FEATURES.md` будет чек-лист ручной проверки в SketchUp 2024 |
| Синтаксис Ruby всех файлов | `ruby -c` |
| Синтаксис JS | `node --check`, если Node доступен |
| Сборка .rbz | Скрипт реально запускается, полученный ZIP проверяется на структуру |

## 11. Интерфейс (кратко)

**Разделы:** одна страница с раскрывающимися секциями.

1. Cabinet Type: категория Base/Wall и тип.
2. Dimensions.
3. Material Settings: выпадающий список существующих материалов модели
   и «New…» с выбором цвета.
4. Construction Settings: крыша, задняя стенка, паз, опоры, шина.
5. Doors and Fronts.
6. Drawers.
7. Advanced Settings: зазоры, отступы, параметры ножек и направляющих.

**Поведение формы:**

- секции, неприменимые к выбранному типу, скрываются. Например, Drawers не
  показывается для верхнего шкафа;
- у всех полей единица «мм»;
- внизу кнопки **Create Cabinet**, **Update Selected** (активна, если выделен
  шкаф плагина), **Reset Defaults** и **Close**.

**Превью (опционально, этап 5).** SVG-вид спереди, построенный из `PartSpec`,
которые возвращает Ruby. Если на этапе 5 оно будет мешать надёжности, это
пойдёт в известные ограничения.
